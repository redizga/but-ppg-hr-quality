# Сделано: E2 — метрики, формат предсказаний, оценщик, тривиальные baseline

Эпик E2 закреплён за Будиловым (`src/butppg/models/__init__.py`, `metrics/__init__.py`).
Реализован и проверен целиком **без реальных данных BUT PPG** — вся эта логика работает
над готовыми числами (предсказания, метки), а не над сырым сигналом, поэтому не зависит
от того, готов ли у Голикова эпик E1. Единственное исключение — `DominantFrequencyHR`,
но и она проверена на синтетическом сигнале (см. ниже).

## Зачем это в первую очередь

Это единственный кусок пайплайна, без которого **не получится оценить вообще ничего** —
ни SIGMA-PPG у Голикова, ни baseline, ни OpenTSLM. До сегодняшнего дня `evaluate.py`
падал с `NotImplementedError` на первом же запуске. Теперь любой, кто сохранит
предсказания в оговорённом формате, может тут же получить метрики — не дожидаясь, пока
кто-то ещё допишет код оценки.

## Что именно реализовано

### 1. Метрики (`src/butppg/metrics/quality.py`, `hr.py`)

- **`quality_metrics(y_true, y_pred, y_prob=None)`** — Macro-F1 (основная метрика,
  по заданию раздел 5), Accuracy, ROC-AUC (если передана вероятность), precision/recall/F1
  по каждому классу, матрица ошибок. Через `sklearn.metrics` — не изобретаем свои формулы
  там, где есть проверенная реализация.
- **`select_threshold(y_true, y_prob)`** — перебор порога классификации (0.005 шаг) на
  валидации, максимизирующий Macro-F1. Закрывает пробел, который мы нашли при сверке
  PLAN.md с заданием: задание прямо требует подбирать порог на валидации (раздел 3), а не
  использовать 0.5 по умолчанию.
- **`hr_metrics(y_true, y_pred)`** — MAE (основная), RMSE (дополнительная), в уд/мин.

### 2. Формат предсказаний (`src/butppg/metrics/predictions.py`)

`save_predictions()` / `load_predictions()` читают/пишут CSV в фиксированной схеме
(`record_id, subject_id, task, y_true, y_pred, prob_good, raw_response, parse_status`),
уже зафиксированной на E0 в `metrics/__init__.py: PREDICTION_COLUMNS`. При сохранении
проверяется:
- все нужные колонки на месте;
- `task` — только `quality` или `hr` (одно значение на файл);
- `record_id` не дублируется;
- `parse_status` — только `ok`/`invalid`/пусто.

Если модель попытается сохранить кривой файл (не хватает колонки, задвоился
`record_id`) — упадёт сразу при сохранении с понятной ошибкой, а не тихо проскочит в
метрики и не даст незаметно неправильную цифру в итоговой таблице.

### 3. Оценщик (`src/butppg/evaluation/evaluate.py`, `scripts/evaluate.py`)

- **`evaluate_prediction_file(path)`** — грузит один CSV, определяет задачу по колонке
  `task`, считает нужный набор метрик, попутно считает долю "невалидных" ответов
  (`parse_status == 'invalid'`) — актуально для OpenTSLM (раздел 6 задания: недопустимые
  ответы не выкидывать молча, а показывать их долю).
- **`evaluate_pipeline(quality_csv, hr_csv)`** — отдельно реализован сквозной сценарий
  quality→HR (раздел 2Б задания), который при сверке PLAN.md с заданием был найден как
  пробел (см. [plan_vs_task_review.md](plan_vs_task_review.md), "Расхождение 2"): раньше
  сценарий был упомянут только в контексте SIGMA-PPG в одном спринте PLAN, без общего
  места в коде. Теперь это одна функция, которую можно применить к предсказаниям
  **любой** пары моделей (baseline+baseline, CNN+CNN, SIGMA-PPG+SIGMA-PPG...), а не
  переписывать логику отдельно под каждую модель. Считает: `accepted_fraction` (доля
  окон, принятых quality-моделью), `false_reject_rate` (доля истинно-хороших сигналов,
  ошибочно отброшенных), `false_accept_rate` (доля истинно-плохих, ошибочно принятых), и
  HR-метрики (MAE/RMSE), посчитанные **только** на принятых окнах.
- **CLI `scripts/evaluate.py`** — ровно интерфейс из README:
  ```bash
  python scripts/evaluate.py --all
  python scripts/evaluate.py artifacts/predictions/sigma_ppg_quality.csv
  python scripts/evaluate.py --pipeline artifacts/predictions/sigma_ppg_quality.csv artifacts/predictions/sigma_ppg_hr.csv
  ```
  Каждый прогон пишет метрики в `artifacts/metrics/<имя_файла>.json` (это коммитящаяся
  директория метрик из `paths.py`) и печатает сводную строку в терминал.

### 4. Тривиальные baseline (`src/butppg/models/trivial.py`)

Обязательны по заданию (раздел 4) как нижняя граница качества для итоговой таблицы:
- **`MajorityClassQuality`** — всегда предсказывает самый частый класс из train.
- **`MedianHR`** — всегда предсказывает медианный HR по **хорошим** окнам train (фильтр
  по `quality_label == 1`, как и остальные HR-модели по заданию раздел 2Б).
- **`DominantFrequencyHR`** — HR по доминирующей частоте PPG-сигнала (без обучения):
  периодограмма (`scipy.signal.periodogram`), пик мощности в физиологичном диапазоне
  30–220 уд/мин (тот же диапазон, что зафиксирован для парсинга ответов OpenTSLM,
  раздел 6 задания), переводится в уд/мин.

Все три следуют общему контракту `fit(train, val, cfg)` / `predict(records) -> DataFrame`,
уже описанному (но не проверенному кодом) в `models/__init__.py` — так что когда Голиков
будет писать `feature_baseline`/`sigma_ppg`, а мы — `cnn1d`/`opentslm`, все модели будут
одинаково стыковаться с оценщиком.

## Как проверено

- `tests/test_e2_metrics.py` — 14 новых тестов: точность метрик на известных числах
  (например, `MAE` и `RMSE` посчитаны вручную и сверены), подбор порога на разделимых
  классах, round-trip сохранения/загрузки предсказаний, отказ при поломанной схеме,
  сквозной сценарий quality→HR на примере с заранее вычисленным вручную ожидаемым
  результатом (4 окна, конкретные false_reject/false_accept), `DominantFrequencyHR` — на
  синтетической синусоиде 72 уд/мин, проверено, что метод восстанавливает частоту с
  точностью до разрешения периодограммы (±6 уд/мин на 10-секундном окне).
- Всего в проекте: **19/19 тестов проходят** (`python -m pytest tests/ -q`), `ruff check`
  — без замечаний.
- CLI `scripts/evaluate.py` прогнан вручную сквозным сценарием: сгенерированы синтетические
  предсказания → `--all`, позиционные файлы и `--pipeline` — все три режима отработали,
  JSON с метриками записался в `artifacts/metrics/`, тестовые файлы после проверки
  удалены (в репозитории не осталось фейковых результатов).

## Что это даёт Голикову уже сейчас

Как только у него появится файл предсказаний SIGMA-PPG в формате
`record_id, subject_id, task, y_true, y_pred, prob_good, raw_response, parse_status`
(достаточно `prob_good`/`raw_response`/`parse_status` оставить пустыми, если модель их не
даёt) — `python scripts/evaluate.py <файл>` сразу посчитает Macro-F1/ROC-AUC/... или
MAE/RMSE, без каких-либо доработок с его стороны. Формат столбцов — единственное, что от
него требуется соблюсти.
