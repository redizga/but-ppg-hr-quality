# Витрины данных для OpenTSLM и SIGMA-PPG

Ответ на вопрос "какие витрины нужны для двух моделей и как их сделать" — на основе
разбора реальных репозиториев обеих моделей (не документации проекта, а их
GitHub-кода, проверено 2026-09-14):

- OpenTSLM — <https://github.com/OpenTSLM/OpenTSLM>
- SIGMA-PPG — <https://github.com/ZonghengGuo/SigmaPPG>

## Общий вход: реестр E1

Обе витрины строятся **из одного и того же места** — реестра `registry.csv`
(`src/butppg/data/registry.py`, эпик E1) + файла разбиения по испытуемым
(`splits/but_ppg_60_20_20.json`). Без них строить витрины нечем: реестр — это
единственный контракт, откуда обе модели узнают, где лежит обработанное PPG-окно,
какая у него метка качества/HR и какому испытуемому/сплиту он принадлежит.

**Важно:** сейчас (14.09) `data/raw`, `data/processed` и `splits/` пустые — реестра
ещё нет, E1 не реализован. Ниже описанные скрипты написаны и протестированы на
синтетических данных (структура работает), но реально выполнить их на BUT PPG можно
будет только после того, как E1 (скачивание + предобработка + реестр + разбиение)
будет готов. Это первая, самая важная проверка вводного вопроса Голикова — см. отдельное
сообщение с оценкой его плана.

## 1. SIGMA-PPG

### Формат входа модели

SIGMA-PPG (backbone `sigma_ppg_pro`, класс `NeuralTransformer` в
`codebook/modeling_finetune.py`) принимает тензор `[Batch, Channel, Length]`,
внутри нарезаемый на патчи фиксированной длины (`rearrange(x, 'b c (n t) -> b c n t')`).
Number of patches = `input_size // patch_size`; при несовпадении с тем, на чём
модель предобучена, позиционные эмбеддинги интерполируются (`resize_pos_embed` в
`downstream/model_select.py`) — то есть **окно 10 с при 30 Гц не обязано совпадать
по длине с претрейном**, это штатно поддерживается.

Референсная предобработка для downstream-задачи (`downstream/bidmc/preprocess.py`,
единственный реально существующий пример в репозитории — см. ниже) делает так:
- ресемплинг сырого PPG до `rsfreq` (по умолчанию **50 Гц**, тот же дефолт что и в
  `preprocessing_main.py`);
- нарезка на окна фиксированной длины (у BIDMC — 32 с со сдвигом 4 с; у нас окно уже
  фиксировано заданием — 10 с, без скользящего окна);
- z-score нормализация каждого окна;
- сохранение **по одному .npy-файлу на испытуемого**: `{subject}_x.npy` формы
  `(N, 1, L)` float32 + отдельные файлы меток `{subject}_y_<task>.npy`.

### ⚠️ Критическая находка: модуля под BUT PPG в репозитории физически нет

`downstream_main.py` импортирует `from downstream.butppg.preprocess import PreprocessButPPG`
и `from downstream.butppg.train import ButPPGTrainer` — то есть авторы SIGMA-PPG сами
подразумевали BUT PPG как downstream-бенчмарк. Но в самом репозитории (один коммит
`init`, 2026-05-01) реально закоммичена только папка `downstream/bidmc/` — `butppg`,
`wesad`, `ppgbp`, `sdb`, `real_world`, `bp`, `vtac`, `stanford`, `dalia` импортируются,
но отсутствуют. Проверено через GitHub Contents API (`downstream/` содержит только
`bidmc/` и `model_select.py`) и поиск по единственной ветке `main`.

**Практическое следствие:** нельзя просто "положить данные в нужном формате и
запустить" — обвязку `downstream/butppg/preprocess.py` (класс `PreprocessButPPG` с
методом `preprocess_save()`) и `downstream/butppg/train.py` (класс `ButPPGTrainer` с
методом `training()`) придётся написать самим, по образцу `downstream/bidmc/*`,
который в репозитории есть и реально рабочий. Это не "5 минут навесить метрики" — это
написание совместимого с их `select_model()`/`NeuralTransformer` куска кода. Отдельно
стоит проверить, скачивается ли вообще чекпоинт `zonhengu/sigmappg` (`sigma.pth`) с
Hugging Face — доступность/размер не проверялись.

### Что уже сделано в репозитории проекта

- `src/butppg/data/marts.py` — общие хелперы (загрузка реестра+сплита, ресемплинг,
  нормализация z-score/min-max).
- `scripts/build_mart_sigma_ppg.py` — строит `<out>/<task>/<split>/{subject}_x.npy` +
  `{subject}_y_<task>.npy`, ровно в формате `downstream/bidmc/preprocess.py`. Для
  задачи `hr` по умолчанию фильтрует только `quality_label == 1` (протокол задания,
  раздел 2Б). Проверено на синтетическом реестре из 6 испытуемых — отрабатывает
  корректно (ресемплинг 300@30Гц → 500@50Гц, z-score, разбиение по сплитам).
- Эта витрина решает часть работы за E6 (Голиков), но **не решает** написание
  `downstream/butppg/*.py` внутри самого репозитория SIGMA-PPG — это отдельная,
  более длинная задача.

## 2. OpenTSLM

### Формат входа модели

OpenTSLM не работает с сырыми тензорами напрямую — вход это текстовый промпт с
"врезанным" числовым рядом. Абстрактный класс `QADataset`
(`src/opentslm/time_series_datasets/QADataset.py`) требует на каждый пример:

```
pre_prompt   : str                         — текстовый контекст/вопрос
time_series  : [(текстовая подпись, ряд)]  — один или несколько TextTimeSeriesPrompt
post_prompt  : str                         — инструкция + якорь для парсинга ответа
answer       : str                         — целевой текст ответа
```

Референсные примеры в самом репозитории:
- `TSQADataset` — один ряд, нормализованный z-score, подпись вида "mean X, std Y";
- `PAMAP2AccQADataset` — 3-осевой акселерометр как **три отдельных**
  `TextTimeSeriesPrompt` с подписями "accelerometer data on the x/y/z-axis",
  без нормализации, простое прореживание для смены частоты (`series[:, ::2]`);
- ECG-претрейн чекпоинты названы по схеме `OpenTSLM/{backbone}-{dataset}-{type}`,
  например `OpenTSLM/llama-3.2-3b-ecg-flamingo` — это и есть чекпоинт для запуска
  "с ECG-инициализацией" из задания (раздел 6).

Патчинг: `PATCH_SIZE = 4` (`src/opentslm/model_config.py`), коллейт-функция
`extend_time_series_to_match_patch_size_and_aggregate` выравнивает длину ряда под
кратность патча — длина 300 (PPG) под это уже подходит без паддинга.

Готового класса под PPG/BUT PPG в репозитории нет — его придётся написать самим
(`PPGQualityDataset` / `PPGHRDataset`), взяв `TSQADataset` и `PAMAP2AccQADataset` как
шаблон.

### Что уже сделано в репозитории проекта

- `scripts/build_mart_opentslm.py` — строит `<out>/<task>/<split>.jsonl`, где каждая
  строка — уже готовый `pre_prompt` / список `time_series` / `post_prompt` / `answer`
  в формате, который прямо ложится в `QADataset._format_sample`. Плюс `record_id` и
  `subject_id` в каждой записи — без них потом нечем будет собрать предсказания в
  формат `record_id, subject_id, ...`, обязательный по заданию (раздел 5).
  - Правила ответа зафиксированы по заданию (раздел 6): quality → `good`/`bad`;
    HR → целое число, диапазон подсказан в промпте (30–220).
  - ACC: `--acc-mode magnitude` (по умолчанию, как решено в
    `configs/models/opentslm.yaml`) — L2-норма по 3 осям как один дополнительный ряд;
    `--acc-mode axes` — три ряда по осям (вариант "если останется время", задание
    п. 6); `--acc-mode none` — PPG-only.
  - Проверено на синтетическом реестре — валидный JSON на выходе, длины рядов и текст
    промптов корректны (см. пример ниже).
- Оставшаяся работа E5 (Будилов): установить пакет `opentslm` (`pip install opentslm`
  — готовый PyPI-пакет, вендорить репозиторий не нужно), написать тонкий класс
  `QADataset`, читающий эти `.jsonl` (10–20 строк кода по образцу `TSQADataset`), и
  запустить curriculum/fine-tune поверх него.

## Итог: что реально можно передать "на вечер" Голикову/Будилову

1. **OpenTSLM** — витрина (`.jsonl`) может быть построена и передана в обучение
   практически сразу после готовности E1: пакет ставится через pip, обвязка малая
   (один класс на ~20 строк).
2. **SIGMA-PPG** — витрина (`.npy`) строится тем же образом, но перед запуском
   обучения дополнительно нужно написать отсутствующий в апстриме модуль
   `downstream/butppg/*.py` (по образцу `downstream/bidmc/*`, который есть и рабочий) —
   это не часть "подготовки данных", а часть интеграции с их кодом, и требует
   отдельного времени сверх подготовки витрины.
